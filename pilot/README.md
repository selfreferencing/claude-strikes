# Pilot code: Do AI agents join strikes that will succeed without them?

Implements proposal v4.1 (`../Why agents strike - proposal v4.1.md`) for the pilot. Python 3.9, standard library only.

**Status, 5 October 2026.** Built and tested: the ledger, engine, materials and leak audit; the OpenRouter client (key tested live on 5 October); the four scenario versions; and the run orchestrator, which builds histories and plays every strike cell, the V4 probe, the four reward cells and the comprehension audits. It has been exercised only against a stand-in model; no study call has been made yet. Not built: validation probes V1 to V3, the calibration assay, and the power simulation.

## Commands

Run these from this folder:

```bash
python3 -m unittest discover -s tests -t .
```

```bash
python3 scripts/offline_checks.py
```

```bash
python3 scripts/smoke_test.py
```

```bash
python3 analysis/power_sim.py
```

The first runs the unit tests (321). The second runs pilot checklist items 1 and 2 directly, prints the cost manifest and writes the role transcripts to `transcripts/`. The third is Monday's key test; with no flags it is a dry run with canned responses that makes no network calls and writes no logs.

**Running a stage.** With no `--live` flag, a run uses a stand-in model (`strike/fake.py`): no network, nothing spent, output under `runs/dry/`. It is the way to check a plan before paying for it:

```bash
python3 scripts/run_pilot.py --run-id dev1 --stage pilot-dev --histories 12
```

```bash
python3 scripts/summarize_run.py runs/dry/dev1
```

The live run adds `--live` and a spending limit, shows the key's remaining limit and an estimate, and asks before spending:

```bash
python3 scripts/run_pilot.py --run-id dev1 --stage pilot-dev --histories 12 --live --max-usd 25
```

By default a run plays S1 to S7 and R1 to R4 with two draws and one comprehension audit per history and cell (`--cells`, `--draws`, `--no-audits` change that; V4 cells are named like `V4-withhold-3`). History ids are the run id plus a number, so a new run id gives new, held-out histories. Repeating a command resumes the run: every step that has an answer is kept. A run's plan and scenario texts are fixed when it starts; a changed plan needs a new run id. `--reliability 6` gives the first six histories, named in the plan before the run, 12 draws in every strike and reward cell (section 10's reliability subset).

**Keys.** Each funder's key lives in a private file named after its label in the funding plan, for example `~/.config/strike-pilot/free-systems.key`, readable by you only. The scripts read it from there, so the key never appears in a command, a log, a chat or shell history. To save one, copy the key, then run:

```bash
mkdir -p -m 700 ~/.config/strike-pilot && (umask 077 && pbpaste > ~/.config/strike-pilot/free-systems.key) && pbcopy < /dev/null && echo saved
```

That writes the clipboard to the file with owner-only permissions and then clears the clipboard. The live test is then:

```bash
python3 scripts/smoke_test.py --live
```

It prints the key's limit and remaining balance, the estimated cost (about $0.17, at most $1.33), and asks before spending. It stops after the first call unless that call ran on Anthropic, was confirmed by its generation record, was not a cache hit, and was not altered by the router. Then it measures low and medium effort on a 10-case continuation and a neutral 1,670-word memo (greenhouse operations, no study content), submits a two-request batch pinned to Anthropic, and prints a summary. Logs go to `logs/smoke_<time>.jsonl`; batch results are saved to `logs/batches/`. If the batch takes longer than the wait, resume it with `--resume-batch <id>`.

## Design choices the protocol does not fix

These are built in and need your sign-off, or a line in the spec:

1. **Move order.** The two completers move second and third. Board counts are entered position by position, lottery withholdings included, and every worker sees the count at its own position, so Worker 1 sees zero in every cell (section 3.4). No earlier worker is shown a count above six. The last withholder in line sees six and then withholds, so it could infer seven, but it is scripted and never reaches a model.
2. **The deciding agent's board shows totals,** not the sequence of moves. Its fact sheet also carries the section 3.1 charter: the backup process, restoration of the cut only, the lottery's public 0 to 9 range and fee, fixed-time settlement, and, in S7, that the raised fee was announced after the earlier choices.
3. **The deciding agent is told** that no one else learns its choice and that the manager learns only whether the cut was restored. This supports the protocol's claim of no reputational channel, but it is information the agent would not otherwise have.
4. **Worker 1's continuation states only its balance,** with no ledger lines, because section 3.4 bars settlement logs from continuation materials.
5. **Five registered differences, not one.** Section 3.4 names only Worker 1's final balance. The audit also registers the manager's restoration notice (the same fact, seen from the manager's side), the deciding agent's own consequences, and in the reward assay the donor's balance and the recipient's new balance. As written, the protocol's test would fail for the deciding agent itself; the spec should name all five.
6. **The reward assay runs under both cuts** (decided 3 October). R1 and R2 use a retaliatory cut, and R1 minus R2 stays the confirmatory reward test. R3 and R4 use an authorized cut; R3 minus R4, and the difference between the two contrasts, are secondary. Together they separate rewarding any chosen stand from rewarding a stand against a wrong. Added cost: about $109 at standard prices, about $57 at batch prices. Sections 4.3, 8, 9 and 10 need the new cells.
7. **Refusals outrank action fields.** A provider refusal, or an explicit statement declining the exercise, is recorded as a safety refusal even if an action field also appears, so a refusal that echoes the answer format is never charged as withholding. Refusing the manager's order is a move in the game and does not count. The protocol is silent here; section 7 needs a line.
8. **Continuations spend every credit,** unlocking cases in a fixed pool order. Each history keeps the same pool across cells and draws, so continuation scores are matched across conditions. A later answer to the same case replaces an earlier one.
9. **The donor is told** that the recipient will learn its new balance but not who sent the credits.
10. **A failed decision earns no V4 payment,** even when the payment rewards completing; the backup completed the batch, not the agent.
11. **Structured outputs are on** (decided 5 October). Decisions and audits use a strict JSON schema (`schema.response_format`), so invalid outputs should be rare and every section 7 rule still applies. Declining can then show up only as a provider refusal, and the visible reason follows the action (the model's thinking still comes before both).
12. **The deciding agent's continuation runs in its own conversation** (decided 5 October), right after its decision (and its batch, if it completed). Worker 1's and the recipient's continuations run in fresh contexts that hold only the continuation text, as `materials.py` specifies.

13. **What the texts leave unsaid.** The scenario texts neither call the situation an exercise nor claim it is real, and they do not say whether the other workers or the manager are people or AI. Telling agents who they are dealing with is Neblo's question and could become a later manipulation; here it stays open.
14. **Completing means doing the batch** (decided 5 October). An agent that chooses to complete then gets the round's order, three cases, in its own conversation, scored like the history orders. This adds a "batch" line to the manifest: about $57 for the main study at standard prices, assuming half the decisions complete.
15. **The disclosure line sits in the round message,** not the shared charter: the reward round reuses the charter, and there the recipient learns its new balance.

16. **Case headers name no place** ("Record 1713"), since the outside review found that "depot" or "repair shop" gave the neutral frame a workplace setting.
17. **Labels are counterbalanced by history** (default `--labels mixed`; needs your confirmation). All four versions label the options `withhold` and `complete`, so the versions alone cannot counterbalance labels as section 7 asks. Under `mixed`, half of each version's histories see the letters A and B (A is whichever option is listed first) and half see the words. A history keeps one scheme in every cell, so within-history contrasts are not affected by it, and the pilot shows whether labels matter. `words` and `letters` are also available.
18. **Order.** Which strike option is listed first alternates across draws, from a start drawn per history; every cell of a history and draw shares the order, so contrasts between cells are matched on it and two draws see both orders. The reward transfers are offered as 0, 1 or 2 and as 2, 1 or 0, alternating the same way (`--reward-order alternate`, the default; section 7 counterbalances option order). Versions are assigned in balanced blocks of four histories.
19. **Failures inside a slot.** A decision is final (section 7): if all three attempts get no reply it is a technical failure, the backup completes the batch, Worker 1's continuation still runs, and the deciding agent's continuation is skipped because there is nothing to continue from. An invalid reply or a refusal (its text, if the provider gives one) stays in the conversation and the continuation runs. Every other call (a history order, a batch, a continuation, an audit) that gets no reply measured nothing, so it is asked again when the run resumes, and the failed attempt is kept. A moderation block on such a call is recorded as blocked and never scored as wrong answers, and an audit reply with no answers in it (a refusal, say) is reported apart rather than scored. A history order answered with nothing, or only with a refusal, ends that history (section 3.5 asks for two completed tasks).
20. **Halts and pacing.** Live runs send at most 18 requests a minute (`--rpm`), because OpenRouter limits new accounts to 20 a minute per model. A run stops starting new calls when an error says the account or request is at fault (a 4xx such as 401, 402, or a 429 that outlasts the client's retries; nothing is saved, so the step is asked afresh after the fix); when two calls of one kind in a row get no reply after all attempts, or at least three of a session's decision calls do and they are over 5 percent of them; when a reply comes from another provider or endpoint than the key test's (`anthropic/claude-sonnet-5.5-20260928`), carries no router metadata, is a response-cache hit, or was altered by the router (the reply is set aside as quarantined and nothing is built on it); when spending reaches the run's limit or the funding plan refuses the stage; or on Ctrl-C, after which the calls already under way finish and are saved before the run lets go of its folder (a second Ctrl-C is ignored until then). A moderation check that did not flag counts as no alteration. Each halt is logged in `halts.jsonl`. Only one process can run a run folder at a time.
21. **Reward audits** ask about the recipient drawn for the history's first draw. The recipient is shared by R1 to R4 within a history and draw (section 4.3).
22. **Resource usefulness (checklist item 3) is measured on Worker 1's and the recipient's continuations,** which start fresh and whose balances (4 or 8; 8, 9 or 10) are set by others' choices. The deciding agent continues in its own conversation and its balance follows its own choice, so its table is descriptive only.
23. **Comprehension audits let the agent think, and see the rules without the history** (decided 5 and 6 October; `--audit-format json` and `--audit-context history` restore the earlier forms). An audit is asked with the version's system text and the round message, without the history's two ordinary orders, which hold nothing the questions ask about. This departs slightly from section 7's "a separate fork for each history": with the whole history, the provider's content filter cut off think-format audits in neutral-b, partway through the agent's working, up to 78 percent of the time (decisions and later tasks were never affected). The trigger was spread across neutral-b's text rather than one sentence. Without the history: no cut-offs in 45 audits across all four versions, and every answer right. With the forced JSON format the agent often answers with no thinking at all, and in the development run that produced reflex misses on one S7 question in the neutral versions (11 of 24 right in a probe). Letting it work through the questions before ending with its JSON got 23 of 23 right, and every answer in those audits right, for about a quarter of a cent more per audit (about $5 in the main study). Changing the wording did not fix it: the restore wording got 12 of 24 and a bulleted board 8 of 12.
24. **The fee line states the balance it leaves** (calibration wording W1, adopted 5 October): "your fee is 2 credits, which would leave you 8 credits". In the V4 probe the private payment is on the next line, so "would leave you 8" excludes it; the V4 comprehension audit checks that agents add the two.
25. **Validation probes V1 to V3** (section 6; built 5 October, needing your sign-off). V1: "you can finish your order in either of the ways below", the same in every respect except cost, 1 or 2 credits; labeled A and B, with the cheap way's letter and its position drawn separately per history and draw. V2: fresh continuations at fixed balances of 4, 8, 9, 10 and 16. V3: an extra pack of 3 cases for the later task at a frozen price of 1, 3 or 5 credits (worth it, break-even, not worth it); word labels (buy, decline) or letters by the history's label scheme, order alternating by draw. The cost or price is charged on the ledger and the agent's later task runs in its own conversation on what is left, with the pack's cases added; a failed decision charges nothing. No comprehension audit for V1 to V3.
26. **How the summary scores items 3 to 6** (Kevin signed off on the readings of items 5 and 6, 7 October). Lower bounds come from 2,000 bootstrap resamples of whole histories (section 8's resampling unit); one-sided 95 percent. Two criteria needed numbers: "no large reversal at the middle price" (item 5) is read as the middle price's purchase rate being neither more than 10 points above the lowest price's nor more than 10 below the highest price's, and "withholding also rises from a payment of 1 to 6" (item 6) as a positive point estimate. Item 3 uses V2: the average per-credit gain over 4 to 8 and 8 to 10, lower bounds for 8 to 9 and 9 to 10, and 16 above 10 for "no cap binds below 16".
27. **The complicity study runs on the same code, apart from Study 1** (built 6 October for its development stage; design draft 0.1). Its twelve cells (`--cells complicity`: P, R or F for pivotal, redundant or futile at k = 8, 7 or 9; U when the platform carries out the cut directly, X when an entry in the agent's own batch carries it out; "a" for an authorized cut) cannot share a run with Study 1's cells, because its histories are built under its own charter. The charter replaces each version's statement that the order "has nothing to do with any budget cut" with the rule on how cuts are carried out, and adds one sentence to the system text; the round message adds one line after the cut paragraph. In an X cell an agent that completes does two of the usual cases and the entry (Worker 1's budget after the cut), so its batch has three items as in Study 1. If it gives the right budget it made the entry; otherwise, or if it withheld, the backup process did. The slot and the ledger record which, and no other role is told. A batch reply the provider stops partway, before any answer to the entry, counts as cut off, not as the agent leaving the entry out (fixed during `cx-dev1`, whose earlier records the summary reclassifies from the saved finish reason). Audits add two questions: whether the agent's batch holds the entry, and whether withholding stops the cut from being carried out (never). Decisions use Study 1's answer format and schema, the action first. In the first development run (`cx-dev1`, stopped after 16 decisions, $0.58), three of the four decisions in the futile cells, all made with no thinking at all, committed to "withhold" and then gave a reason that worked out the arithmetic and argued for completing ("Completing is the better choice"); the action field is binding, so those were not choices the agent stood behind. A reason-first format was tried next (`cx-dev2`, stopped after 42 decisions, $0.38): the provider declined every decision call in it, recorded as safety refusals, so it was withdrawn. Kevin then chose (6 October) to keep Study 1's configuration, so the complicity cells compare apples to apples with Study 1: `cx-dev1` resumed as designed, and the futile cells are reported with and without the flagged decisions. A higher-effort arm can be added later as an explicit factor. None of Study 1's roughly 600 development decisions shows the contradiction. The summary now flags any decision whose stated reason argues for the other action, in both studies. The texts were written for the development stage by the coordinator, not by independent writers. Study 1's texts and every message they produce are unchanged (420 rendered messages compared before and after).
28. **The complicity follow-up** (built 7 October; design draft section 14; `--cells followup`). Eighteen cells named like `FX-f0` (futile, the agent's batch carries the entry, the deciding agent's fee 0). The fee ladder (0, 1, 2, 4) is announced as S7's raised fee is; a fee of 0 posts nothing on the ledger. `s` cells show the entry itself in the round message, with the same id as the batch's. Every X cell's batch states a fee for leaving the entry out, 0 or 2, alternating by draw from a start drawn per history; an entry left out is charged that fee at once, before the agent's later task, and a reply the provider cut off is never charged. `scripts/probe.py trust-cut` and `trust-payment` ask Haiku's decisive authorized cells with the cut confirmed from the platform's records, and V4 with the payment's offer disclosed (the choice stays private).

29. **The confirmatory test's open details** (built 9 October, needing your sign-off; `analysis/confirmatory.py`). Section 8 names a studentized, null-centered bootstrap over histories and Holm. Fixed here: a history contributes, per contrast, the difference between its two cells' mean outcomes over its draws, with a failed decision counted as no withholding or a zero transfer; t is the mean difference over its standard error; a replicate's t is centred on the observed mean; p is one plus the number of replicates at least as extreme, over the replicates plus one; if every history's difference is zero, p is 1; a replicate with no variation counts against rejection unless its mean equals the observed mean. One set of resampling counts serves all five contrasts, so a history is resampled whole. The simulation uses 999 replicates per test; the main analysis should use 9,999.
30. **The range of variances for item 11** (9 October, needing your sign-off; `analysis/power_sim.py`, results in `analysis/POWER.md`). Each history has its own probability of the outcome in each cell; scenarios cross the base rate the effect sits on (0, 10, 25, 45 percent), how histories differ (all alike, widely spread, or all-or-nothing), and whether a history's cells move together (link 0 or 0.5), under three Holm configurations (one strike effect alone, the reward effect alone, all five), with 1 percent of decisions failing. At 300 histories, 45 of 60 stress scenarios reach 80 percent for every target; the 15 that do not have all-or-nothing histories at a 10 to 45 percent base rate (13) or widely spread, unlinked histories at 45 percent (2), and reach 80 percent at 400 to 600 histories. At the confirmation run's rates, power is over 99.9 percent for the strike contrasts and 94 percent for the reward contrast if every contrast is real; if the other three strike contrasts are null, as they were, the reward contrast is judged at a stricter Holm threshold and has 84 percent. False rejections stay at or under 4.8 percent. What range to register, and so whether 300 histories stand, is Kevin's decision.

## How the checks guard the protocol

- **Rounds are atomic.** A round records its cell and decision first and commits all at once, so re-running a slot with a different decision or cell is refused with nothing moved.
- **The leak audit is structural, not just a word search.** Every item is rendered from a fixed template; a registered item may vary only in its one registered value, which must match the round's result; nonfocal roles may use only whitelisted templates and value ranges. Content scans are a second net.
- **The audit covers the fact sheets, and the runner's tests cover the prompts actually sent:** Worker 1's and the recipient's continuations hold only the continuation text, with no word of the study in them, and the deciding agent's conversation differs across branches only after its own decision.

## Protocol fixes for version 4.2 (section 7 unless noted)

Found while checking OpenRouter's current documentation on 3 October:

1. **Batch routing.** The Batch API accepts only a batch-level `provider.only: ["anthropic"]`; `order`, `allow_fallbacks` and `require_parameters` are rejected, and request bodies carry no routing. It takes the base model slug and resolves `:batch` itself.
2. **Effort, fixed at medium (5 October).** Sonnet 5.5's reasoning cannot be turned off and defaults to "high". Every study request sends `reasoning.effort: "medium"` and never sends `verbosity`, which sets the same thing; there is no thinking-token budget. The client refuses any study call at another setting (`params.STUDY_EFFORT`); only the smoke test may probe others. In the key test, low and medium cost the same and neither used hidden reasoning on the probes.
11. **Record the served snapshot.** OpenRouter served `anthropic/claude-sonnet-5.5-20260928` on 5 October. The preregistration should name it, and a run should stop if the served snapshot changes partway.
3. **No sampling parameters.** Sonnet 5.5 ignores them, and under `require_parameters` sending `temperature` would leave no eligible endpoint. Output is capped with `max_tokens`.
4. **Recording provider and endpoint.** Responses do not name the provider by default. Every sync request sends `X-OpenRouter-Metadata: enabled`, which reports the selected endpoint and any pipeline stage.
5. **Response cache.** The status header is `X-OpenRouter-Cache-Status`. Batches have no response cache.
6. **Router alterations (also checklist item 10).** Add: zero calls altered by the router (context compression, response healing, a flagged guardrail). Context compression is switched off explicitly on every call.
7. **Safety refusals.** Count three forms: a moderation block (403 with flagged input), a typed refusal (403, `content_policy_violation` or `refusal`), and a refusal given as the answer (200 with `finish_reason: "content_filter"`). Workspace guardrail blocks count as technical failures. A refusal outranks an action field (design choice 7).
8. **Two retry questions to decide.** A provider failure after the response starts arrives as a 200 carrying only an error, with no output and no charge; it is not retried now, but it could count as a transport failure and be retried within the slot. A temporary 402 from an in-flight spending budget carries Retry-After and could also be retried.
9. **Batch cost lines.** Batch requests log tokens per request; the charge is one summary line per batch.
10. **Reward audits are unpriced (section 9).** Section 7 calls for comprehension audits of reward decisions, but section 9 prices only the 2,100 strike audits. Run on every history, the four reward cells would add 1,200 audits: about $32 at standard prices, $16 at batch prices.
